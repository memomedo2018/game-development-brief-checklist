Engineering review resources

A config key cannot install code your game does not contain

Remote configuration is useful when the shipped game already understands the setting. It does not make a new mechanic appear merely because somebody adds a key to a dashboard. This runnable, dependency-free example helps a producer and developer agree that boundary before a live event.

Run the review locally

Download both files into the same directory and run the test with Node. Nothing connects to Unity, a game account or a live configuration service.

  • config-boundary.mjs — review function
  • config-boundary.test.mjs — ten synthetic checks
node config-boundary.test.mjs

The example accepts a bounded enemy-speed multiplier, a boolean for an already implemented event, and an integer stage limit. These are invented review values, not recommended game balance numbers. Unknown keys, incompatible schemas, wrong types, non-finite numbers and out-of-range settings reject the entire candidate and retain the prior accepted values. Inputs are not mutated.

Inspect a candidate before you call it a release

import {review} from './config-boundary.mjs';
const result = review({
  schema: 1,
  values: {enemySpeed: 1.2, eventEnabled: true}
});
console.log(result);

Now add newWeapon: true to that candidate. The result rejects it because the local policy does not declare that key. In a real project, the team must decide whether an existing system can express the proposed change. If new code, content delivery or an updated binary is required, it needs its own production and release process rather than an unexplained config exception.

Why reject the whole candidate?

A partial update can combine a new event toggle with an old limit or an invalid multiplier. For this small model we choose all-or-nothing acceptance so the resulting state is explicit. That is a design choice, not a claim that every production service behaves this way. Your team may need another policy, but it should be agreed and tested instead of inferred from a successful dashboard save.

Three review conversations the code cannot replace

  1. Supported build: identify which shipped version understands the schema and whether older clients require another configuration.
  2. Apply boundary: decide whether a newly accepted value takes effect immediately, at the next match or after restart. This function does not schedule application.
  3. Recovery evidence: compare the expected state after a rejected candidate, service timeout and restart. This example only handles supplied values; it does not fetch, persist or authenticate them.

Unity's Remote Config overview describes its key-value tuning and override model. The review function here is independent sample JavaScript, not an implementation of that SDK or a substitute for service permissions, validation or operational monitoring.
