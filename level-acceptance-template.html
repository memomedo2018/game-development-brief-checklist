Playable Level Acceptance Card

Copy this card when a team needs to agree what one level must prove. The existing project brief establishes the overall engagement; this worksheet turns a single playable route into observable outcomes. It includes a deliberately small checkpoint example, a completion truth table and a revision log. It is not a client test report.

Use it in four steps

  1. Replace the example with your own player goal and starting assumptions.
  2. Agree the required conditions before the first review; leave unresolved choices marked unknown.
  3. Record expected versus observed behavior against a named build and level revision.
  4. Retest a changed condition before closing the acceptance decision.

Download the editable CSV matrix. Open it in a spreadsheet, duplicate rows as needed and attach authorized review evidence. This static page has no form submission, account requirement or telemetry code. Browser printing can produce a review handout.

Worked example: reach a checkpoint after clearing a threat

Suppose a small mission should finish only when the player is alive, reaches the endpoint and resolves one required threat. Those three conditions must hold together. An optional side route is not a completion requirement. This is a hypothetical rule chosen to demonstrate the worksheet, not an assertion about any published game or a universally appropriate mechanic.

Example completion truth table
AliveEndpoint reachedThreat resolvedExpected result
YesYesYesOne completion transition
YesYesNoRemain active; explain remaining objective
YesNoYesRemain active; continue to endpoint
NoYesYesFailure route, not victory

Check both ordering routes: resolve the threat first, and reach the endpoint first. Then repeat the completion input or trigger. Agreement that a rule is correct is distinct from evidence that its implementation works. The CSV therefore begins with an empty observed-result column and a pending status, never a prefilled pass.

These are example hypotheses, not findings from our tests. Keep footage, input conditions and revision identifiers with actual observations. Do not convert hesitation into a retention forecast or ask for unrelated art changes to solve an objective-state defect.

What this worksheet deliberately excludes

It does not establish economy balance, campaign difficulty, final environment quality, device performance, multiplayer authority or release readiness. Those require their own scope and evidence. Unknown is an acceptable entry; inventing a passed test is not. Keep commercial acceptance and any legal agreement separate from this operational review aid.

For the decision framework behind goals and encounter pacing, read Upload For Software's game level design guide. The worksheet supplies reusable rows; the guide explains which production decisions those rows support.
