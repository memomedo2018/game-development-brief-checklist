Which build did you actually review?

A screenshot can show a useful observation while leaving the identity of its build unclear. This small resource keeps the source declaration, production inputs, artifact digest and human review decision in one card. It is a local comparison aid, not a build system or a certification.

Two questions that should stay separate

First, are the declared inputs the same? Second, are the delivered artifact bytes the same? A renamed file may still contain the identical artifact. A new source revision can be declared while somebody accidentally supplies yesterday's file. A changed binary can also result from packaging details even when the recorded source and settings look unchanged.

The tool reports these relationships rather than deciding whether a build is good. A digest is an identity signal for bytes, not proof that the file was produced from the named source. The input record is a declaration that a reviewer must corroborate against the actual build procedure.

Place the files in the same directory. No package installation, account, network connection or API key is needed. The example is explicitly synthetic and starts with an empty artifact digest and a pending review decision. Do not substitute it for your project's real values.

node build-review-card.test.mjs
node build-review-card.mjs stamp build-review-card.example.json build-review-fixture.txt > baseline.json
node build-review-card.mjs compare baseline.json baseline.json

The stamp command reads only the card and explicit artifact path supplied on the command line, computes SHA-256, and prints a new card to standard output. It does not overwrite the input card, execute commands from it or run Unity. Choose a new output filename. Hashing a large build may take time, so the artifact is read as a stream.

Record the inputs that can change the outcome

The required identity fields are build ID, full source revision, Unity version, target and recipe ID. The inputs object is where your team records relevant declarations such as scene list, package-lock reference, configuration revision and build options. Add the actual toolchain or other production inputs your review needs; this example cannot discover missing dependencies.

Object key order does not change the comparison. Array order is retained because changing a scene list or ordered option list may matter. Build ID is a label, so changing that label alone does not change the input fingerprint. Artifact digest is compared separately.

  • artifact_evidence_missing: at least one card has no artifact digest.
  • declared_inputs_differ: the recorded source, environment, recipe or input values differ.
  • same_declared_inputs_different_artifact: the declarations match but the digests do not; investigate without assuming a defect.
  • same_declared_inputs_and_artifact: supplied declarations and digests match. This is still not acceptance or proof of a reproducible build.

Leave the decision with the reviewer

The card retains a human decision of pending, accept, needs_work or blocked. A non-pending decision requires both a note and a review-record reference. The checker validates that these fields exist; it cannot establish that the referenced review happened or that the decision is correct. Matching digests never automatically set the decision to accept.

For a practical review, record the device or environment, repeatable route, expected behavior and observed result in the referenced review record. Compare that evidence with the artifact actually delivered. Keep private build URLs, access tokens, customer files and player data out of public examples and repository issues.

Eighteen assertions were run for the published tool, including input changes, key-order stability, renamed build labels, missing or malformed digests, decision-field requirements and actual hashing of temporary text files. These are synthetic tool checks, not Unity execution, device testing, security verification or client acceptance.
