Unity Handover Evidence Manifest

A folder of source files is not a review record. This small, dependency-free resource helps a recipient notice missing evidence before closing a handover: which revision, which build, which instructions and which unresolved cases?

The checker validates field structure only. It does not build Unity, inspect licenses, verify credentials, locate artifacts or certify a delivery. Filled fields can still contain incorrect claims; a recipient must inspect the referenced evidence.

Download the three working files

  • Example JSON manifest — deliberately incomplete; all observations start blank and pending.
  • Node manifest checker — no dependencies, network calls or execution of supplied commands.
  • Structural tests — synthetic inputs, not a report of a Unity test.

Run locally

Save the files together. Review the source before running it. Use a locally installed Node.js runtime; no package installation is required.

node handover-evidence-check.test.mjs
node handover-evidence-check.mjs handover-evidence.example.json

The unchanged example should return gaps and exit code1. Copy it to your own file and replace placeholders. Exit0 means its required fields are complete; it is not an approval decision. Parse or input errors return2.

Review the five boundaries

CaseRecipient action
Clean buildFollow the recorded editor/package/build instructions on the agreed recipient environment. Compare the output identity to the review record.
Asset sourcesOpen editable sources and confirm that runtime exports and license records map to the agreed assets.
Save continuityReview the supported installed-update route, backup/recovery decision and any excluded migration paths.
Service ownershipConfirm who owns each required account and where configuration is documented. Keep secrets outside this manifest.
Known limitsCheck that unresolved defects and deferred work have a documented owner and disposition.

Separate expected from observed

Write the expectation before review. Afterward record what actually happened, the artifact reference and status. An observation can describe a failure; the checker does not infer a pass from the word “observed.” A not-applicable case needs a reason and a review-record reference, not a silent checkbox. Add game-specific cases rather than treating these five as exhaustive.

Keep private information private

Use review identifiers or access-controlled references. Do not publish passwords, access tokens, account recovery material, customer data or private project paths in a public example. The checker does not scan for secrets. Local JSON is read only to report structural gaps and is never submitted by this tool.

Attach a recipient decision

After inspecting evidence, record accepted, changes requested or blocked in your own project decision log, including who reviewed it and the revision. That decision is separate from this checker. For the wider buyer-facing file list, see the game source handover guide (Arabic).
