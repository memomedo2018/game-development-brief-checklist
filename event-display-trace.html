A game event can happen first and appear second

A screen recording shows presentation. It does not, by itself, establish when a game rule changed state. This executable example separates the time an event occurred from the time its corresponding feedback was displayed.

Two events, two orders

Consider a hypothetical pickup followed by damage. A delayed pickup notification appears after the damage feedback. The example uses invented milliseconds from one monotonic clock; it is not a captured Unity trace or a client result.

Event IDOccurredDisplayedDelay
pickup10ms35ms25ms
damage12ms20ms8ms

Occurrence order: pickup → damage. Presentation order: damage → pickup. Reviewing only the visible notifications would reverse the apparent order. That observation does not prove that damage was applied before the pickup.

Run the fixture

Download the three files into one folder. Use Node.js to run the dependency-free checker. It makes no network requests and only reads the JSON file you explicitly provide.

Checker source · Example JSON · Synthetic tests · Expected example output

node event-display-trace.test.mjs
node event-display-trace.mjs event-display-trace.example.json

The result keeps both orders and calculates each event’s display delay. It deliberately returns accepted:false: sorting a trace does not accept gameplay, decide whether a delay is tolerable, or validate a game build.

Capture the boundary you are reviewing

In an actual review, agree what occurredMs records: an input, accepted command, authoritative state change, or presentation request are different boundaries. Agree what displayedMs records as well. Creating a UI object is different from proving pixels reached a display.

Give the event and its presentation the same correlation ID. Retain the build revision, test setup, capture point and clock definition. If a notification is never shown, keep it as an unmatched event in the evidence rather than silently removing it. This small paired-row checker requires complete pairs and is not a missing-event detector.

Do not subtract a server timestamp from a client timestamp without a justified clock relationship. Clock offset and drift can invalidate the apparent delay. Even on one clock, a stable ID tie-breaker only makes output repeatable; it does not prove causal order for simultaneous timestamps.

Use the trace to ask a better question

When a reviewer reports “damage happened first,” compare state-change evidence and visible feedback independently. Was the underlying result incorrect, was feedback late, or was the recording too coarse to resolve the boundary? Keep the observed result separate from the expected rule. Define an acceptable delay and visual behavior for the target build before declaring success.

The checker validates unique IDs and finite, nonnegative same-clock times. It rejects a display time earlier than its paired event. It does not infer device latency, packet ordering, frame presentation, synchronization quality or a production performance improvement.

For the related decision of which game events to instrument and how to review their meaning, see the Unity event-contract and analytics acceptance guide. This resource complements that guide with a separate runnable timing fixture.
