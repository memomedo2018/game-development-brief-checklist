A successful callback is not the same as one accepted grant

This small synthetic model gives reviewers a concrete way to discuss duplicate callbacks, pending decisions and later revocation. It is a proposed acceptance aid, not evidence of tests executed against a real store or game.

Boundary: this code does not validate receipts, contact Apple or Google, persist state, authorize a purchase or protect a live economy. The event labelled verified is a test input, not proof that a transaction was verified. Never connect it directly to production fulfillment.

Download and run locally

Save both files in one folder. Requires a maintained Node.js version with the built-in test runner. No dependencies, credentials, account identifiers or network calls.

node --test entitlement-review.test.mjs

What the examples decide

  • Pending or rejected events do not grant the synthetic product.
  • The first verified product/transaction pair grants once; replaying that identity does not add another grant.
  • A revocation removes a previously granted unit once. In this model a late verification cannot revive the revoked identity.
  • Different transaction identities remain separate. Missing identity and unknown status fail explicitly.

The model intentionally counts generic units by product. A permanent unlock, consumable pack and subscription require different real fulfillment and recovery rules. Product-plus-transaction identity is a convenient fixture key here, not a universal cross-store identity design. Real platform identities, server trust, account ownership, subscription state, restore semantics and migration are outside this example.

Use it to ask better acceptance questions

Before a real review, agree the product type and authoritative grant owner. Then create authorized sandbox transactions and record the tested build, platform, delivery identity, observed entitlement and result after reopening. A fresh process resets this sample's in-memory state; it does not demonstrate durable duplicate protection, concurrency safety or recovery after a crash.

Try a deliberately repeated delivery and compare the number of accepted fulfillment operations with the visible entitlement. Treat an attractive success animation as feedback to check, not an independent source of authority. Record an actual observed result separately from the expected outcome.

For the wider commissioning boundary, the mobile game in-app purchase acceptance guide discusses verification, fulfillment, restoration and the evidence to request from the implementation team. This resource remains a narrow runnable discussion model rather than a replacement for that integration.

Known limits

No real receipts or customer information are included. The tests prove only the behavior of this small function for their stated fixtures. They cannot establish store compliance, fraud resistance, cross-device restoration, a complete refund policy or that a customer has received the right purchase.
